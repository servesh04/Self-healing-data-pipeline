# Expansion review and implementation plan (P0–P3)

**Status:** P0 implemented and verified in the working tree on 13 October 2026; P1–P3 remain planned. The isolated full-graph evaluation passed 11/11 fixtures against the configured live database and LLM.
**Inputs:** the three-direction proposal, `docs/design-p0-value-drift-multi-patch.md`, and the current repository.
**Decision:** The directions are useful. The P0 implementation follows the corrections below; the later phases retain their proposed order and verification gates.

## Deliverable 1 — Review of the three directions

| Direction | Assessment | Recommended change |
|---|---|---|
| 1. New drift classes | Value drift is a strong next example. Distribution and temporal drift add monitoring, but are different from schema repair. | Define each signal by contract check and action. Keep statistical/range anomalies alert-only. Treat date *format* repair as a separate parsing feature, not as a temporal-range alert. |
| 2. Smarter healing | Combined patches and rollback address real limitations. Approval history is valuable, but the proposed precision formula and threshold changes are unsafe without labeled outcomes. | Build conflict-aware batches, versioned mapping writes and rollback first. Record decisions and outcomes before attempting adaptive thresholds or few-shot retrieval. |
| 3. New sources | Multiple contracts are the right prerequisite for new sources. The database and JSON proposals currently blur sampling, validation, normalization and external API access. | Introduce a source interface and bind each run to a named contract and mapping version. Deliver database tables and local JSON separately; add live HTTP fetching only after security and pagination policies are explicit. |

### Corrections required before P0 coding

1. **Reverse the value-drift fixture.** `config/contract.yaml` already allows `North, South, East, West`. The draft's full-word `day7` would be clean and its proposed `North → N` map would break validation. Make the source use `N, S, E, W`, and map them to the full words. If the contract changes later, derive expected labels from that contract instead of embedding them in a prompt.
2. **Expose the actual evidence.** `profile_source.py` currently records three sample values, not distinct values; `diff_contract.py` exposes expected dtypes, not allowed sets. A value specialist needs bounded distinct values/frequencies from the raw source and the contract's allowed values. High cardinality or truncated samples must force review or escalation.
3. **Split validation failure kinds.** `diff_contract.py` currently classifies uniqueness failures and any unrecognized check (including numeric minimum failures) as `value_violation`. Only a categorical `isin` failure on an allowed-value column is eligible for value mapping. Keep check identity and counts in each finding. Row-count, uniqueness and numeric-bound failures remain unhealable unless separately designed.
4. **Keep diagnosis authoritative.** The draft's multi-patch router dispatches on the number of raw failure kinds *before* checking `drift_class`. It can auto-run specialists after an `unknown` diagnosis, including the unfixable case. Batch only diagnosed, individually admissible findings. An unknown or unaccounted finding blocks automatic application of the whole batch.
5. **Use confidence per component.** The current `diagnose` emits one class and one confidence for one proposed fix. That confidence cannot authorize unrelated patches. Extend diagnosis to a list of candidate fixes with finding IDs and confidence, while preserving a single-candidate compatibility path. Use the minimum component confidence for the batch; any ambiguity sends the whole atomic proposal to human review.
6. **Define conflicts and state reset.** Different classes do not guarantee independent changes: a rename changes the target name for casts or value maps, and two proposals can touch the same key. Normalize all proposals to post-rename column names, reject duplicate/conflicting writes, and clear candidate outputs at the start of each heal cycle. Do not let old `specialist_outputs` override a later single proposal.
7. **Finish the schema and UI work.** The draft omits `DiagnoseOutput`'s regex change in `backend/graph/schemas.py`. `PatchDiff.jsx` would render a nested value map as `[object Object]`; `mappingDiff.js` ignores it; `GraphCanvas/topology.js` has a fixed node list; analytics assumes one specialist string. These need explicit implementation and verification.
8. **Avoid an empty or ineffective write.** Current `apply_patch.py` increments `heal_attempts` even when persistence fails and records `applied_patch` regardless. The expansion should reject empty patches, record persistence outcome and mapping version, and only call a patch applied after the insert succeeds. P1 adds full versioned rollback.

The current P0 design doc remains a useful starting sketch. Its claims that no frontend work is needed, that value checks are already fully described by `diff_contract`, and that mixed drift can be routed by failure-kind count should be superseded by this plan.

## Cross-phase design decisions

### Data and run identity

- Make `source_ref = {type, source_id, options}` and `contract_name` explicit run inputs, while retaining `source_path` as a compatibility field for existing CSV runs. Resolve IDs server-side; never accept arbitrary database connection strings or HTTP URLs in a run request.
- Persist `contract_name`, `source_ref`, `mapping_scope`, mapping version read at start, and eventual version written with the run record/checkpoint. Current `mapping_state` is scoped only by `pipeline_env`; from P1 it is scoped by `(pipeline_env, contract_name)` or an explicit pipeline ID. Migrate existing rows to the default contract without losing history.
- A run uses a pinned contract snapshot/version. A mapping patch must be a compare-and-swap write against the version it read. On a version mismatch, re-read and revalidate or escalate; do not overwrite another run's change.
- Keep a typed `Finding` with check code, column, expected constraint, actual examples/count, and a stable finding ID. A `FixCandidate` has specialist, covered finding IDs, patch fragment, confidence, rationale, and safety status. Preserve `history` as append-only and store the complete batch as one heal attempt with component metadata.

### Safety and measurement

- A patch may only use registered operations and contract-compatible targets. For categorical maps, accept only known expected labels, require explicit coverage of observed unexpected values, preserve nulls and legitimate existing values, and check for mapping collisions and key types. Mapping a genuinely new business category needs human confirmation or a contract change.
- One batch gets one approval decision, one mapping write and one `heal_attempts` increment. If any component is unknown, low-confidence or conflicting, route the whole batch to review or escalate; never silently drop the bad component and auto-apply the rest.
- Verification counts must be comparable: use stable failure IDs and severity, not just the number of Pandera failure rows. A patch is successful only when full validation passes. In P1, rollback a persisted version after a failed rerun that worsens checks or violates protected assertions.
- Keep each eval fixture isolated by mapping namespace/contract and publish baseline versus graph outcome, attempts, human decisions, exact patch, and failure delta. The existing eval script currently auto-approves low-confidence proposals; report that separately from unattended success.

## Deliverable 2 — Detailed implementation plan

### P0 — Categorical value repair and safe combined patches

**Outcome:** a new `N/S/E/W` fixture heals to the contract's full region names in one attempt; the existing rename-plus-type fixture can heal in one atomic attempt; the unfixable and ambiguous fixtures still escalate or pause appropriately.

1. **Establish fixtures and baseline.** Add deterministic day7 value-drift generation and a mixed case that includes a categorical repair. Include negative fixtures for a new/ambiguous category, numeric-minimum failure, uniqueness failure, and the existing `day5_unfixable`. Add the new dataset to the dashboard picker and eval matrix. Capture expected first-run failures from the current Pandera contract before changing graph behavior.
2. **Make findings precise.** Extend `FailureCase`/`DriftItem` or add a typed finding adapter in `pipeline/contract.py` and `graph/nodes/diff_contract.py`. Preserve the originating check name and distinguish `enum_value`, `unique`, `minimum`, `row_count`, `dtype`, `null`, and schema findings. Expose allowed values from the selected contract. Add bounded distinct-count/frequency profiling for categorical columns in `profile_source.py`, with an explicit `truncated` flag and no unbounded prompt content.
3. **Add the value patch.** Extend `MappingPatch` in `pipeline/mapping.py` with `value_maps`; validate outer columns and target values against the selected contract at proposal/application time. Apply mapping after renames and before final validation in `pipeline/steps.py`, preserving nulls and unmapped legitimate values. Define merge semantics for multiple maps on the same column: deep merge only when keys are disjoint and targets agree; otherwise report a conflict.
4. **Add the specialist and diagnosis schema.** Implement `ValueSpecialistOutput`, `spec_value`, and prompts. Change `DiagnoseOutput` validation as well as the prompt. For mixed drift, produce structured candidates covering specific finding IDs, with one confidence per candidate. Allow a single candidate to continue through the existing path. A value candidate is admissible only for an `isin` failure with known allowed labels and sufficient observed coverage; unknown/unhandled findings stay visible.
5. **Compose one atomic proposal.** Have a coordinator invoke only the needed scoped specialists with their own finding group, validate each result against its narrow schema, normalize post-rename column names, detect overlaps, and produce one `MappingPatch` plus component metadata. Sequential specialist calls are acceptable initially. The coordinator must not dispatch if diagnosis is `unknown`. Clear proposal-related state each cycle. Keep `propose_patch` limited to rationale generation; it must not invent patch content.
6. **Apply and report accurately.** Validate nonempty merged patches before the confidence gate. Use the minimum candidate confidence. On approval, first test the candidate against an immutable copy of the source and check that no protected assertion regresses; then persist one complete mapping snapshot with a minimal compare-and-swap check on the mapping version read by this run. Record the new ID. If validation or save fails, escalate with an error and no false `applied_patch`. Update `rerun_validate` history with component specialists, patch/version, and observed result. Update `PatchDiff`, mapping timeline, graph topology, analytics and run detail for nested maps and multiple specialists.

**P0 verification gate**

- Unit tests: enum detection excludes uniqueness/minimum; allowed-set and bounded-profile extraction; valid and invalid value maps; null/unmapped behavior; conflict detection; renames plus cast/value targeting; empty patch and stale-state rejection; every routing branch including `unknown` plus mixed failure kinds.
- Graph tests with stubbed LLM outputs: day7 heals in one attempt, day4 heals in one batch, low-confidence batch interrupts and resumes, rejection leaves mapping unchanged, failed specialist does not result in partial auto-apply, and `day5_unfixable` applies no patch.
- Real local pipeline run against all fixtures; then an isolated full-graph eval when DB and LLM credentials are available. Check final mapping snapshots and API/UI rendering, not just terminal status. Preserve original six-case behavior except day4's planned two-to-one attempt improvement.

**Likely files:** `backend/pipeline/{contract,mapping,steps}.py`, `backend/graph/{state,schemas,routing,build}.py`, `backend/graph/nodes/{profile_source,diff_contract,diagnose,propose_patch,apply_patch,rerun_validate,spec_value}.py`, prompts, fault generator, eval, tests, and the listed frontend components. Update the P0 draft to match these acceptance rules before using it as a coding checklist.

**P0 closeout (13 October 2026):** The final live sweep passed all 11 fixtures. Five drifts healed unattended in one attempt, including the combined rename/type case and the new value and mixed cases. The ambiguous rename required review at confidence 0.4; the eval harness simulated approval and then verified resume and healing. Four unsafe cases escalated without a mapping write. Inspection of the saved results found no introduced validation failures and confirmed the expected exact mapping snapshots, including `N/S/E/W` to the allowed region labels. The local suite passed 122 tests, the frontend built, and Python compilation passed. See [eval_summary.md](eval_summary.md) and the raw `eval/results/eval_results.json` generated by the sweep. The eval uses a live database for mapping persistence and an in-memory graph checkpointer; a separate production Postgres checkpointer/API/UI run is outside this P0 eval result.

### P1 — Contract isolation, rollback, and calibration evidence

**Outcome:** each run is bound to one named contract and mapping scope; a worsening persisted patch can be reverted safely; specialist outcome data is trustworthy enough to display. Adaptive thresholds remain opt-in until calibrated on labeled cases.

1. **Multiple contracts (3C).** Move the current contract to `config/contracts/default.yaml` with a compatibility loader for `config/contract.yaml`. Add a validated `ContractRegistry` that rejects duplicate/unknown names and records a content hash/version. Add `contract_name` to `POST /api/runs`, run state, run records, pipeline calls, mapping state and the dashboard selector. Partition mapping history and analytics by pipeline/contract. Migrate old runs and rows to `default` with idempotent SQL; exercise a second contract whose columns differ.
2. **Versioned writes and rollback (2C).** Extend P0's compare-and-swap guard to immutable mapping version IDs and parent IDs, with a per-scope current pointer and transactional writes. Capture pre-patch mapping version and a stable failure/severity baseline. After rerun, if protected assertions regress or the patch fails a defined worsening rule, append a rollback event/version restoring exactly that run's parent version only if the current pointer still equals the failed version. If another run changed it, escalate for reconciliation. Surface rollback cause and both versions in run history/dashboard. Ensure rejected proposals never write.
3. **Calibration data (2A).** Store one proposal/decision/outcome record per specialist component, including auto versus human decision, patch version, contract, dataset family and labeled correctness when available. Do not call `validation passed` or `human approved` precision: validation checks only declared constraints, and approvals are selected by low confidence. Display counts, approval rates and labeled correctness with denominators and confidence intervals. Keep the existing 0.75 threshold as a floor/default; only enable specialist-specific thresholds after a preset minimum of independently labeled examples and an offline regression comparison. Never lower the threshold solely because a handful of proposals passed validation.

**P1 verification gate:** migration preserves default behavior and run resume; concurrent writes cannot lose an update; rollback restores the exact prior mapping with audit history; a second contract has isolated mapping and correct API/UI selection; calibration aggregates exclude pending/unlabeled proposals and are reproducible from event rows. Evaluate old and new threshold policies offline before any auto-apply behavior changes.

### P2 — Distribution alerts, database tables, and approval examples

**Outcome:** a numeric shift can be reported even when schema validation passes; a named database table can run through the same contract checks; approval history can be inspected and safely used as optional prompt context.

1. **Distribution drift (1B).** Add baseline profiles per contract/source identity with sample size, missingness, quantiles and robust spread; capture version and collection window. Define minimum sample size and missing-data behavior. Compare the new batch to the baseline using a documented statistic and threshold chosen on held-out fixtures; `>2σ` of a changed mean alone is not an adequate rule. Mark this as `alert`/`escalated` without mapping writes. The graph must invoke monitoring on clean schema passes as well as after successful repairs. Add day8 (10× revenue), a normal-variance control, and low-sample cases.
2. **Database source (3A).** Introduce `CSVSource` and `DatabaseTableSource` behind a common load/profile interface. Config contains named, allowlisted, read-only connections; secrets come from environment or a secret store, never committed YAML. Resolve schema/table identifiers safely, use a deterministic bounded sample for profiling and materialize a bounded complete snapshot for Pandera validation. Reject datasets beyond the declared cap until cross-page checks (including global uniqueness) are implemented. Set row/time limits and document snapshot consistency; never equate `LIMIT 1000` profiling with complete validation. Extend the API and dashboard with source IDs, not raw SQL.
3. **Approval examples (2D).** Record approval/rejection after `interrupt()` resumes, idempotently keyed by run and proposal so replay cannot duplicate it. Store rationale, contract, finding shape and final validation outcome. Review/redact sample data before prompt inclusion. Retrieve only same-contract, same-specialist, labeled, relevant examples with capped text and deterministic ranking; treat them as untrusted data in prompts. Compare blinded/held-out proposal quality with and without examples before enabling retrieval by default.

**P2 verification gate:** clean-but-shifted day8 alerts without patching; controls do not alert; database sample and full validation agree on row counts and failures, including a fault beyond row 1000; unknown source/table requests fail closed; approval events are idempotent across resume/restart and examples cannot supply patch operations outside the specialist schema.

### P3 — Temporal monitoring, date parsing, and JSON normalization

**Outcome:** date range/freshness anomalies alert with a clear reason; supported format changes can be parsed through a constrained mapping operation; local nested JSON records can be normalized for contract validation.

1. **Temporal drift (1C).** Define per-contract rules such as maximum future skew, freshness lag and expected historical window using an explicit timezone and run clock. Profile parsed-date counts, min/max and invalid count. Range/freshness anomalies are alerts, not format patches. For a format-only dataset, add an allowlisted `date_parse` operation with explicit format and locale/timezone, run it before transform, and revalidate. Avoid pandas' implicit ambiguous MM/DD versus DD/MM guesses. Test day9 format change, future-date anomaly, stale data and ambiguous dates separately.
2. **JSON source (3B).** Add local `JSONSource` first, with a documented records path, bounded depth, configurable separator, collision policy, null behavior and array policy. Flatten deterministically before the common pipeline; make `flatten_rules` validated config only if source-level defaults cannot represent the need. Keep flattening separate from categorical value repair. Add a named HTTP API source only with explicit authentication, URL allowlist, pagination, retry, rate-limit, payload-size and snapshot semantics.
3. **Finish product surfaces.** Show alert-only findings distinctly from failed assertions and attempted patches. Let run history, source picker, contract selector, mapping timeline and analytics represent all source types and multiple drift components. Update `README.md`, `ARCHITECTURE.md`, `DASHBOARD.md`, and the eval summary from measured outcomes.

**P3 verification gate:** format repair succeeds only for declared formats; future/stale data alerts without mapping writes; malformed or ambiguous dates escalate; nested JSON flattening rejects collisions and unexpected arrays; CSV and database regressions remain green; API pagination tests detect missing/duplicate records.

## Execution and release gates

| Gate | Required evidence |
|---|---|
| Before each phase | Freeze fixtures and expected outcomes; add schema migration and compatibility notes where state or API changes. |
| Every change | Run focused unit/graph tests and the full local suite; build the frontend when UI contracts change. |
| Before deploying a phase | Run isolated full-graph eval, inspect mapping/audit rows and run-detail rendering, and compare against the previous phase's fixture matrix. Use human approval in a separate manual interrupt/resume check; the automated eval's approval is synthetic. |
| Release decision | Record false auto-applies, unintended mapping changes, alerts on controls, time/LLM cost, and known limitations. Zero false auto-applies on the named negative fixtures is a hard gate; new source types must pass isolation and full-validation checks. |

**Verification environment:** The local `.venv` Python launcher points to a missing Python 3.14 installation. P0 tests and the live evaluation used a Python 3.12 runtime with the project dependencies; the temporary compatibility wheels were removed after the run.
